# Domain Permission and Resource Mapping Register

**Document ID:** ARC-IAM-MAP-001  
**Status:** Recommended logical mapping baseline selected under the product owner's delegated decision mandate — 2026-11-19  
**Authority:** ODR-005 sections 16.39–16.42; ARC-IAM-CAT-001 section 15; ARC-IAM-CTRL-001; ARC-AUTH-MATRIX-001; FRS; ERS; Business Rules Catalogue; State Transition Matrix; RTM.  
**Purpose:** Provide one cross-module register linking canonical atomic permissions to conceptual resources, resource scopes, lifecycle controls, sensitive data boundaries and owning domain specifications for a dairy SaaS product ranging from owner-operated businesses to multi-Branch enterprises.

## 1. Status and source-of-truth rules

This register maps business resources and operations to the canonical keys in [Permission Catalogue and Assignment Governance](PERMISSION_CATALOGUE_AND_ASSIGNMENT_GOVERNANCE.md) section 15.2. It does not define new permission semantics and does not assign permissions to anyone. Section 15.2 remains the single source of truth for key identity and metadata; this register is the resource/lifecycle/scope mapping index.

The entries below cover **692 canonical keys across 204 resource namespaces**. A key may appear only once in this register. Any new core key must first be registered in ARC-IAM-CAT-001 through its catalogue-change governance. Unknown, retired, ambiguous or unmapped protected operations fail closed.

**API boundary:** Concrete HTTP route names, controller method names, RPC symbols and event/job identifiers are intentionally not invented because the project is still in documentation-only phase and those contracts have not been designed. Before implementation, each conceptual command/read/export/job/device/integration operation must be mapped to its exact API/command/event identifier and tested against the same canonical key(s). This register supplies the business resource and permission decision layer; it is not a speculative API contract.

**Assignment boundary:** A listed key denotes a capability that may be made available to an eligible Tenant within its scope. It is not automatically granted by Tenant membership, account type, role name, job title, employee status, Home/Primary Branch, plan entitlement, feature activation, device/client type or extension installation. The Tenant may assign eligible keys directly or through governed groups and editable permission bundles within the assigner's delegation ceiling. Explicit deny prevails; permission expiry/revocation applies across all channels.

## 2. Global mapping and enforcement rules

1. Every protected operation resolves exactly one primary conceptual resource/action key where possible; an operation with multiple effects must validate every affected permission independently.
2. Permission and resource scope are separate. A key without a valid Tenant/Branch/location/task/person/financial-period/data-class scope is insufficient. Resource ownership and Tenant membership are also validated independently.
3. Every view/list/search/detail/aggregation/drill-down surface must be explicitly covered by the permission metadata. Search counts/facets/autocomplete cannot reveal unauthorized data. Export/download requires dedicated permission plus row/field permissions and download-time revalidation.
4. Standard lifecycle actions remain independent: view/list, create, update draft, submit, assign, execute, capture, verify, approve, reject, publish, post, reverse, reconcile, export, configure, administer and delete/archive are not interchangeable.
5. The owning domain's state machine defines when an action is legal. A permission cannot bypass an invalid state, ownership rule, approval, quality/safety hold, stock reservation, financial period or resource-availability constraint.
6. Approval permissions and workflow approval requirements are separate. The actor must hold the domain action/approval permission and satisfy the matched immutable ApprovalPolicyEvaluationSnapshot. Generic workflow routing or task assignment creates no authority.
7. Fixed platform/domain safeguards prevail over Tenant policy and extensions. Tenant policies may add controls, narrow scope, lower limits and require more evidence/review; they cannot weaken fixed rules.
8. Every protected write revalidates membership, effective allow/deny, resource scope, grants, policy version, limit and current state at commit. Concurrency and idempotency rules apply to API, mobile/offline, jobs, events, devices and integrations alike.
9. A role or permission bundle remains an editable convenience package. The same effective permission/scope/context yields the same result regardless of bundle label or human title.
10. Extension keys are registered namespaced capabilities, separate from core keys. Registration, installation, activation and credential creation do not grant data access.

A sensitive-field permission does not create general parent-record permission. Likewise, having parent-record permission does not automatically disclose sensitive fields. The permission metadata in ARC-IAM-CAT-001 section 15.3 must declare the precise field/data categories, masks, row scope, query surface, export eligibility, audit and retention.

The following categories require distinct treatment:
- Personal identity and legal identification documents, including uploaded/verified proof and identifiers.
- Party/customer/supplier/farmer bank and payee details, account evidence and payment references.
- Customer contact/address and delivery-location information, purpose-limited to assigned operations where relevant.
- Employee/workforce records, engagement terms, attendance evidence, compensation, salary, payslips, bank details and statutory data.
- Tax identifiers, legal registrations, compliance certificates and statutory documents.
- Stock valuation/cost and commercially sensitive pricing/rate information.
- Payment, cash, bank statement and reconciliation evidence.
- Delivery proof, signature/OTP, photographs, GPS/location and temperature/device evidence where enabled.
- Security credentials, device/session metadata, support investigations and sensitive audit records.

For each enabled module, the final field-level implementation map must identify: canonical parent resource key; exact sensitive-field key(s); row/resource scope; permitted query surfaces; download/export permissions; purpose limitation; masking; evidence verification state; audit event; retention class; and API/report/file/job enforcement points. A broad report or export permission never bypasses the underlying field/row permissions.

## 5. Approval and state binding

The resource action keys above are evaluated with ARC-IAM-CTRL-001:
- R0/R1 operations normally require the exact permission, scope and state validation; no artificial second-party setup is imposed unless a fixed rule or Tenant policy requires it.
- R2 high-impact operations use separate approval by default under the selected policy baseline. Tenant-selected INR, percentage, quantity/UOM, data sensitivity and export thresholds are configured in versioned ApprovalPolicyProfiles.
- R3 critical operations require dedicated privilege and purpose-bound controls; fixed non-delegable rules and emergency boundaries cannot be relaxed.
- Every approval request stores the exact source payload/version and immutable ApprovalPolicyEvaluationSnapshot. A stricter new policy adds/repeats required stages; a less restrictive policy does not relax an existing pending request. Ambiguous scope/unit/policy conflicts fail closed.
- Stock-task grants and ApprovalDelegation are not permissions. The underlying domain key, membership, scope and special grant/delegation conditions must all be satisfied independently.

**State coverage rules**
- The mapping applies to the actual transition, not merely because an actor can open the parent screen. View keys do not imply submit, approve, post, execute, release, reverse, export or configure.
- Where a transition creates a separate ApprovalRequest, also require `approval.request.submit`; a decision requires `approval.action.approve` or `approval.action.reject` plus the exact domain approval permission and effective policy. If no ApprovalRequest is required by fixed rule or Tenant policy, do not manufacture an approval step.
- If a transition changes stock and physical custody, validate the independent inventory key(s) and custody handover/event key(s). A custody event is not a StockMovement; a StockMovement does not prove physical acceptance.
- A special grant/delegation (StockTaskAccessGrant, ApprovalDelegation, SupportAccessGrant or workforce/resource assignment) is an additional condition only. It never creates the domain action permission or broader data visibility.
- Any state transition not listed here, or any transition added to an owning domain state machine, is not automatically authorized by a nearby key. Register the exact canonical key(s) through the controlled mapping process before implementation; missing/ambiguous mapping fails closed.

## 6. Small-to-enterprise operating profiles

The mapping is common across all Tenant sizes. Scale changes enabled capabilities, assignments, policy values, integrations and operational controls—not permission semantics.

| Operating profile | Configuration examples | Invariant |
|---|---|---|
| Owner-operated / micro dairy | One authorized user may receive multiple operational keys; one Branch, manual records, minimal employee/asset/fleet setup; no artificial second approver for R0/R1 actions unless fixed or configured control requires it | Exact permissions and scope remain required; owner title alone grants nothing; stock-owner grant approval and fixed emergency controls remain mandatory |
| Small team | Direct or small-bundle assignments; limited Branch/site scopes; chosen thresholds for discounts, stock variances and refunds; optional maker-checker | Every action remains separately permissioned; revoke one key without removing unrelated access |
| Multi-Branch | Governed groups/editable bundles; Branch/location scopes; separate read/report vs mutation; cross-Branch stock grants and delivery assignments; Branch-specific approval policy | Shared premises or Home Branch does not grant access; cross-Branch scope is explicit, effective-dated and audited |
| Enterprise | Fine-grained direct/group/bundle assignments; dataset/field scopes; quorum/multi-stage approvals; delegated approval only for eligible actions; service/extension identities; higher data volumes | Same canonical keys and fixed policy semantics; no role/title hierarchy or unrestricted wildcard permissions |

## 7. Implementation-readiness gates

Because the project has not yet defined physical API routes or implemented modules, the following are **explicit pre-implementation gates**, not assumed-complete work:
1. For every FRS command, query surface, state transition and exception, identify the canonical resource key(s) and exact allowed effect.
2. For every API route/command/event/job/device/integration operation, record its concrete contract identifier, primary resource, affected resources and complete required key set.
3. Map every sensitive field and data category to its exact registered view/download/export key(s), mask and purpose.
4. Map every resource to Tenant/Branch/OperatingLocation/StockLocation/person/task/financial-period ownership and cross-Branch rules.
5. Bind each approval-triggered transition to its exact ApprovalPolicyRule, threshold unit, reviewer/quorum, delegability and required ApprovalPolicyEvaluationSnapshot.
6. Produce allow/deny/scope-mismatch/explicit-deny/expiry/revocation/role-neutrality tests for every key/resource/channel.
7. Add the exact identifiers to RTM and QES; a module cannot pass documentation or implementation readiness with an unmapped protected operation.
8. Re-run the canonical-key coverage audit after any catalogue change.

No HTTP route names or API symbols are invented in this register. The final API-to-key mapping requires the approved API architecture and module endpoint contracts at the subsequent implementation-design gate.
